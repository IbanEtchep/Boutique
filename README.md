
### Module folder

Boutique needs Artisan with the add-on API 2.12.0 or newer. Build with `./gradlew build` (tests, then `build/libs/Boutique-<version>.jar` with HikariCP shaded in); the API version is `artisanApiVersion` in `gradle.properties`. Its menus, dialogs, texts, catalogue and settings live in `plugins/Artisan/modules/boutique_addon/`, the module's folder, listed under the Boutique module in the editor. The folder keeps the former project id, so Versions, drafts and qualified references (`boutique_addon:…`) carry over. On the first start with this version, Artisan moves an existing `plugins/Boutique/editor/` there once; while both folders hold files, the old one stays in use and the log says so. The `project_id` line older versions wrote in `manifest.yaml` is removed at startup. Migration archives (`shop.yaml.migrated`, `catalog-icon-backup/`, `category-kind-backup/`) stay in `plugins/Boutique/`, and `plugins/Boutique/migrations.done` lists the one-shot migrations already run (delete a line to run it again). The plugin writes its folder at startup and asks Artisan for nothing: Artisan reads a registered folder on the next tick and calls the module's `onReload()`, which loads the catalogue from that folder only (needs the Artisan v2 of 2026-10-21 or newer). The price formats of a legacy `config.yml` replace the bootstrap's defaults once; afterwards the defaults set by an admin are kept.

### Catalogue categories

The catalogue is one `boutique_category` Document per category, `boutique_categories/<id>.yaml` in the module's folder (schema `boutique_category/v1`; the file name is the id). A category has `name`, `icon`, `discount` (whole percent), an optional `order` (rank in the main menu, lower first; without one, after the others, by id) and `items`: each with `id`, `name`, `icon`, `price`, an optional `discount` and `actions` (a keyed action chain, or an Action DSL string from older catalogues). A text is a string or one string per language (`{fr: …, en: …}`). Keys the shop does not know are kept.

The kind is declared by the module (`BoutiqueModule.categoryKind()`); the editor view ships in the jar as `src/main/resources/artisan-editor/ui.js`, built from `editor/` against `@artisan/editor-sdk` 1.7 (`cd editor && npm install && npm run build`; the SDK comes from `editor/vendor/`, packed from Artisan with `npm pack`). In the editor, categories can be created only in the Boutique folder; each one is a canvas node listing its articles (icon, name, price after discounts) and is edited in the Properties panel, then published with the folder's draft and Déployer. An editor older than SDK 1.7 does not load the view.

At every start, `CategoryKindMigrator` moves the former `data/categories/` Table to these Documents: the rank in `_source.yaml` becomes `order`, a name that was a key of the default language takes its text, and the other languages kept in `lang/` at the Table's addresses go along. Each original is copied to `plugins/Boutique/category-kind-backup/` first; a category whose Document already exists is never overwritten and stays in the Table (the log names it). While Documents are missing, the shop still reads `data/categories/`, then `boutique/shop.yaml`. A Boutique draft opened in the editor before the update still holds the Table: discard it before deploying, or the deployment writes the Table back (the shop keeps reading the Documents, and the next start lists those categories as left in the Table).

### Catalogue icon lore

Product presentation belongs to `icon` (title, lore, quantity and attributes). The item model no longer declares a separate product `lore`. At startup, `CatalogIconMigrator` moves existing row lore into an icon extension before Artisan loads the project. The captured item lore is preserved without a placeholder: Artisan keeps the base item lore and renders the icon lines below it. Original files are backed up in `plugins/Boutique/catalog-icon-backup/`, outside the editor project; each replacement is atomic and the migration is idempotent. Canonical translations are copied to the new icon addresses; old keys remain available to legacy references. Generated templates inherit the icon lore and append the price.

### The `/boutique` command

`/boutique` is a command of the module (`boutique:open`, API 2.11.0): it opens `boutique_addon:shop_main`, and is always reachable as `/boutique:boutique`. Artisan writes it as the command file `commands/boutique.yaml` of the folder (`open_menu: boutique_addon:shop_main`) and replaces it with each new version while it is untouched: its name, aliases, permission, description and behaviour change in that file, from the folder in the editor like any command. An edited file stays the admin's, and Reset in the editor puts the module's version back. At startup, the `commands/boutique.yaml` that older versions of Boutique wrote (it has an `id`) is removed with its `manifest.yaml` entry while it is still the shipped one, so that Artisan writes its own. A changed one is kept and becomes the module command's file.

The menus and the dialog the code opens by id (`menus/shop_main.yaml`, `menus/shop_category.yaml`, `dialogs/confirm_purchase.yaml`) are system elements of the folder (API 2.12.0): Artisan writes them from the jar when they are missing and replaces them on a new version while they are untouched. An edited one is kept, and the editor says the module ships another version. The editor never deletes or moves them; Reset brings back the shipped file. `SYSTEM_MENUS_VERSION` in `BoutiqueModule` goes up with every change to these files.
